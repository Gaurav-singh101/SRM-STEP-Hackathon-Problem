**Measured, not claimed.** Produced by
`uv run python -m tests.tools.sql_plans --rows 2000000 --vehicles 5000`,
which creates a throwaway database, loads it, measures, and drops it.

| Field | Value |
|---|---|
| Date (UTC) | 2026-09-29 |
| Commit | recorded by the commit that adds this file |
| PostgreSQL | PostgreSQL 16.15 |
| Rows in `idle_events` | **2,000,000** across 5,000 vehicles |
| Rows in `vehicle_daily` | 880,511 (**2.3:1** compression — see the leaderboard finding below) |
| Partitions | 4 monthly range partitions |

## What these numbers are, and are not

The rows are **generated by the script, not produced by the pipeline**. They exist
to give the planner realistic cardinality and selectivity at a scale where index
choice actually changes the plan. Nothing here is a claim about platform
throughput or about end-to-end latency; the only claim is the *relative* cost of
the same query with and without the index it was designed around.

The demo database holds about 2,600 idle events. At that size PostgreSQL correctly
sequential-scans everything, so plans taken from it would prove nothing.

The "before" case has the index genuinely absent rather than disabled with
`enable_indexscan = off`, because a disabled index scan falls back to a bitmap scan
and the comparison stops meaning what it appears to mean.

ranges overlap, the change is reported as **no measurable difference** rather than
as a ratio: on a contended laptop a ratio between overlapping ranges is a number
with nothing behind it.

## What the measurement says

**Three of the shipped indexes are transformative.** Keyset pagination, the partial
`excessive` index and the per-vehicle history each move from a sequential scan to an
index scan and gain two orders of magnitude. Those three are earning their storage.

**No index rescues the raw-events leaderboard.** Across runs its index has measured
anywhere from no detectable effect to about 2x - check the table above for this run -
and the reason it never does better is structural: a 30-day window over one tenant is
a large fraction of the table, so PostgreSQL correctly prefers a sequential scan. A
query that has to read most of the rows cannot be indexed out of it. **In every run,
with or without the index, the raw path stayed above the 200 ms target.** That is the
durable result; the exact factor is not.

**Reading the daily rollup instead is a clear win, and it is what the endpoint now
does.** Comparing the two variants as they actually ship - both with their indexes
present - the rollup path is roughly **3x faster**, and the two ranges do not
overlap in either of the two independent nine-sample runs used to confirm it. At this
scale it also lands **under the p95 < 200 ms target**, while the raw path does not.
`vehicle_daily_leaderboard_idx` earns its place too: a genuine 2x on the rollup
query, again with non-overlapping ranges.

The reason the gain is around 3x rather than an order of magnitude is the compression
ratio above. Each rollup row replaces only a couple of event rows at this event
density, so the rollup query is a smaller version of the same shape of work. What
matters more than the constant factor is what the cost grows *with*: the rollup path
scales with **vehicle-days**, bounded by fleet size times window length, while raw
aggregation scales with **events**, which is unbounded as telemetry frequency rises.
At 100,000 vehicles and billions of events those diverge sharply.

### How this number was nearly got wrong, twice

This is the methodological finding, and it is why the ranges are published.

An earlier version of this script took the median of **five** runs and printed that
single number. On a contended laptop the ordering of the two leaderboard variants
reversed between passes: one said the rollup was faster, the next said the raw query
was, and one pass even showed `vehicle_daily_leaderboard_idx` making its query
*slower* as the planner traded a parallel sequential scan for a bitmap heap scan.
Each of those readings was publishable-looking and two of the three were wrong.

Three changes fixed it: nine samples instead of five, the full min-max range printed
beside every median, and a refusal to print a ratio at all when the two ranges
overlap. Where a `no measurable difference` verdict appears in the table above, that
is the rule firing rather than a formatting quirk: the ranges genuinely overlap, so
no ordering exists to report. A claim was then only accepted once two independent
runs agreed on it with non-overlapping ranges - which is why the rollup comparison is
stated as a result and the raw path's own index factor is not.

### Still worth doing
The 200 ms target is met here at two million events on one laptop, which is not the
same as meeting it for a 100,000-vehicle fleet. The next step if it becomes tight is
a coarser pre-aggregate than a daily one: a window-level rollup keyed on
`(tenant_id, window_end, vin)` with the window totals already summed, turning the
request into an index range scan plus a top-K over **one row per vehicle** instead of
a `GROUP BY` over thirty. Not built, and not claimed.

No latency figure here is a platform number. This is one laptop, one PostgreSQL
container and generated rows - which is exactly why the ranges are published
alongside the medians.
